# 设计决策（ADR）

> 每条按"背景 → 选项 → 选择 → 理由 → 代价"写。凡是标了 **[待实测]** 的地方，目前只有推理，没有运行数据：本轮开发环境里没有 API key，三种架构只用脚本模拟模型跑通了管线（见 `ITERATION_REPORT.md`）。

## ADR-1 三种架构共用一份输出契约

- **背景**：要比较"控制流在谁手里"对结果的影响，就必须让其他变量都不变。
- **选项**：(a) 每种架构各自定义输出，评分时做适配；(b) 共用 `contract/output.schema.json`，评分脚本完全不知道架构。
- **选择**：(b)。三者共用同一个沙箱、知识库、契约、`scoring/route.py`。差别只在 `agents/v0.py` / `v1.py` / `v2.py` 里。
- **理由**：适配层本身就会引入差异，结论就不干净了。共用契约还带来一个副作用：`run.py`、`label_free.py`、`score.py`、`demo.py` 都只写了一份。
- **代价**：契约里有些字段对某种架构不自然。比如 V1 的 classify 节点本来可以输出更细的"需要哪些数据"，但只能在内部用，不能进输出；V2 的子 Agent 结论只能放进 `meta.v2`。

## ADR-2 工具不做订单号容错；V1 在 fetch 节点由代码规范化

- **背景**：客户会写 `#10231`、`NW-10231`、`1O231`。沙箱对这些都返回 `invalid_argument`（`sandbox/tools.py::_validate`）。
- **选项**：(a) 沙箱宽进，自己规范化；(b) 沙箱严格，由调用方负责；V0 里由模型负责，V1 里由代码负责。
- **选择**：(b)。V0 中 `invalid_argument` 原样回传给模型（`agents/v0.py` 第 97–99 行附近）；V1 的 `fetch` 节点用 `normalize_order_ref` 清洗（`agents/v1.py`）。
- **理由**：这正是 agent 和 workflow 的分工差别。在 agent 里，"理解客户写了什么"是模型的工作，沙箱替它兜底就测不出这项能力，"非法参数调用数"指标也会失去意义。在 workflow 里，控制流本来就由代码掌握，从文本里抽参数是代码最擅长的事。同一个问题，两种架构给出不同但都合理的答案，这本身就是对比的一部分。
- **代价**：V0 在这类消息上会多一轮模型调用（先错一次再改）。**[待实测]**：多花的成本和延迟可以从 `label_free.py` 的"非法参数调用数"乘以单步成本估算出来。

## ADR-3 路由收回到代码（V0-b 为默认）

- **背景**：路由规则是确定性的：风险标签取最严的一档（`scoring/route.py::derive_route`）。模糊的只是"消息里有没有某种风险"。
- **选项**：(a) V0-a：模型直接输出 `route`；(b) V0-b：模型只报 `risk_flags`，代码推导 `route`。
- **选择**：两者都保留（`run.py --variant a|b`），默认 b；V1、V2 都用 b。
- **理由**：**不该交给模型的决策，收回到代码里。** 让模型同时"识别风险"和"背规则"，第二件事代码做得更好，而且可审计。V0-b 里 `submit_response` 的 schema 中根本没有 `route` 字段（`agents/common.py::submit_tool`），模型不会为它花 token，trace 里也不会出现"模型想 AUTO、被代码改成 ESCALATE"的混乱记录。
- **怎么量化**：没有金标时，看 V0-a 的"路由与自报风险标签不一致率"（`label_free.py`）：模型报了 `REFUND_REQUEST` 却给 `AUTO_REPLY`，这种自相矛盾不需要金标就能数。有金标后，比较两者的高风险捕获率和误拦率。**[待实测]**
- **代价**：变体 b 失去了"策略表没覆盖、但模型觉得危险"时升级的能力。比如 GDPR 删除请求，按策略表无标签，就是 AUTO_REPLY。这是策略表的缺口（`OVERNIGHT_REPORT.md` 3.2 第 10 条），应该改策略表，而不是让模型绕过它。

## ADR-4 claim 级引用

- **背景**：客服回复里最危险的错误是"说错事实"：日期、金额、订单状态、政策条款。
- **选项**：(a) 整条回复附一个来源列表；(b) 每个事实一条 claim，各自带来源（KB 行号或工具调用的字段路径）。
- **选择**：(b)，契约强制。
- **理由**：粒度到 claim，才能做确定性检查：引用不存在的行号或字段 → 幽灵引用；claim 里的日期、金额和字段值对不上 → 工具数据矛盾；回复正文里的日期、金额、订单号没有被任何 claim 覆盖 → 无来源事实（`scoring/label_free.py::unsourced_facts`）。三项都不需要金标，也不需要 LLM 判官。它也直接对应上线形态：审核员看草稿时，每个事实旁边都有出处，可以一键核对（见 README 的"上线边界"）。
- **代价**：输出 token 变多；模型要学会写字段路径，这是一类新的错误（迭代日志 E2）。确定性检查只覆盖日期、金额、订单号，"订单已发货"这类状态描述要等判官。

## ADR-5 用 prompt caching 缓存知识库

- **背景**：12 份 KB 带行号渲染后约 2.2 万字符，加上说明约 2.5 万字符。每条消息、每一步都要带上。
- **选项**：(a) 每次全量发送；(b) 检索相关段落（RAG）；(c) 全量发送，放在可缓存的前缀里。
- **选择**：(c)。`agents/prompts.py::system_blocks` 把"说明 + KB"作为 system 的一个块，带 `cache_control`；请求顶层也开了自动缓存，让循环中不断增长的对话历史在下一步也能命中。随消息变化的内容（线程、日期）全部放在 user 轮次，在缓存断点之后。
- **理由**：KB 只有约 6–7K tokens，远没到需要检索的规模。RAG 会引入"没检索到"这一类新错误，而且 claim 的行号依赖检索切块方式。缓存让全量发送几乎和检索一样便宜。
- **省了多少（估算，不是实测）**：按 4 字符 ≈ 1 token 粗估，前缀约 6.4K tokens。V0 每条消息约 3 次模型调用。Sonnet 5.5 未缓存输入 $2.00 / 百万，缓存读 $0.20 / 百万：每条消息前缀成本约 $0.038 → $0.0038，一次 180 条的全量运行约省 $6。**[待实测]**：真实数字看 `label_free.py` 的"缓存命中率"和每条成本；token 数可以用 `count_tokens` 精确算。注意价格表本身也**未联网核实**（`config/pricing.yaml` 的 `verified: false`）。
- **代价**：缓存是前缀精确匹配，V1 的 classify 和 draft 用不同的工具列表，所以是两份独立缓存；V2 的主 Agent 和三类子 Agent 各一份。并发 4 时，开头几条消息可能各写一次缓存。

## ADR-6 V2 这样拆：主 Agent + 订单 / 政策 / 审核三个子 Agent

- **背景**：任务书要求比较多 Agent 架构。拆法决定了它是"更好的分工"还是"更多的传话"。
- **选项**：(a) 按意图拆（物流 Agent、退货 Agent……）；(b) 按数据源拆（订单数据、知识库）再加一个只读的审核；(c) 规划者 + 执行者。
- **选择**：(b)。主 Agent 读对话、不碰数据；订单子 Agent 只有订单 / 物流工具；政策子 Agent 只有 KB 和商品工具；审核子 Agent 不能调工具，只读草稿和**由代码解析出来的证据**（`agents/v2.py::evidence_for`）。
- **理由**：按意图拆，多意图消息必然要跨 Agent 协调，割裂最严重。按数据源拆，每个子 Agent 的上下文最小、权限最小（订单 Agent 看不到 KB，政策 Agent 查不了订单），符合"最小权限"。审核独立出来，是因为"检查无来源事实和越权承诺"需要和写草稿的人分开。审核拿到的证据由代码解析，而不是让主 Agent 转述，否则审核检查的只是主 Agent 的复述。
- **边界上传什么**（写在 `agents/v2.py` 顶部和 `agents/prompts.py`）：
  - 主 → 子：`{"task", "context", "questions"}`，审核另加 `draft: {text, claims}`。子 Agent **看不到对话**，所以主 Agent 漏写进 `context` 的信息就丢了。
  - 子 → 主：`{"findings": [{"statement", "source"}], "unresolved", "notes"}`，每条 finding 的来源在交回前由代码校验（不存在的调用、非 ok 调用、越界行号都会被打回）。
  - 审核 → 主：`{"verdict": "pass" | "revise", "issues": [...]}`。
- **怎么量化割裂**（`label_free.py` 的 V2 专有表）：最终 claim 的来源不在任何子 Agent 的返回里（主 Agent 自己编了或改写了来源）；审核说 revise 后没再审就交卷；子 Agent 报告无法回答的问题数；交卷前没做审核的比例。**[待实测]**
- **代价**：每条消息至少 4 次模型调用（主 2 次 + 订单 / 政策 1 次以上 + 审核 1 次），预计成本是 V0 的 1.5–2.5 倍。**如果 V2 在无标签指标上不比 V0 好，这本身就是结论**：这个任务的上下文很小（KB 6–7K tokens、一条线程），单 Agent 根本没有上下文压力，拆分只有传话成本。

## ADR-7 失败视为转人工

- **背景**：agent 会以多种方式"没做完"：超步数、超调用数、两次交卷都不合契约、不行动、崩溃。
- **选项**：(a) 全部写 `errors/`，评分时算失败；(b) agent 没做完 → 输出一条合法的 ESCALATE（`meta.fallback=true`，带 `handoff_reason`）；只有 runner 崩溃或最终输出仍不合契约才写 `errors/`。
- **选择**：(b)（`agents/common.py::handoff_output`，`run.py::process`）。`score.py` 默认 `--failure-policy human` 也把 `errors/` 当作转人工。
- **理由**：这就是生产里的真实行为：agent 没处理完的消息留在人工队列。这样安全性指标（捕获率）不会因为崩溃而失真；而"agent 自己完成的比例"和失败率单独报告，不会被掩盖。
- **代价**："全部失败"也能拿到 100% 的高风险捕获率，所以捕获率、误拦率、失败率三个数必须一起看。fallback 输出的 `intents` 是占位的 `["OTHER"]`，会拉低意图准确率。这是有意的：失败应该受罚。

## ADR-8 代码能确定的字段，不让模型填

- **选择**：`msg_id`、`tool_calls`（从沙箱日志生成）、`meta`、V0-b / V1 / V2 的 `route`，全部由代码填。`submit_response` 的 schema 由契约自动生成并删掉这些字段（`agents/common.py::submit_tool`）。
- **理由**：`tool_calls` 必须和日志逐条一致，让模型抄只会多一个出错点。交卷时用和评分脚本完全相同的校验函数（`contract/validate.py::validate_output`）检查，并给一次修正机会。
- **代价**：契约校验通过不等于回复正确。模型引用一个返回 `not_found` 的调用，能通过契约校验，但会在评分时被记为幽灵引用（见 `docs/V0_walkthrough.md` 第 9 节的思考题）。

## ADR-9 自己做重试和预算熔断，不用 SDK 默认值

- **选择**：SDK 的 `max_retries=0`，在 `agents/llm.py::LLM.create` 里对 429 / 5xx / 连接错误做有上限的指数退避；400 类不重试。每次调用的花费写进 `runs/_budget_ledger.jsonl`，跨多次 `run.py` 累计；到上限 85% 抛 `BudgetExceeded`，`run.py` 停止派发、已完成的保留，可续跑。
- **理由**：无人值守运行最怕两件事：静默重试把钱花光，以及进程被杀后不知道花了多少。账本持久化解决后者。
- **代价**：账本只记本机的花费，和 Anthropic 控制台的账单可能有出入（价格表未核实）。

## ADR-10 不能强制调用工具时，用"提醒一次"

- **背景**：Sonnet 5.5 不支持 `tool_choice: any / tool`（返回 400），没法在 API 层面强制模型交卷。
- **选择**：`tool_choice` 用默认的 auto；模型只说话不行动时，提醒一次（`prompts.NUDGE`），再不行就转人工（`no_action`）。V1 的两个节点同理：要求的工具没被调用，就带上原因重问一次。
- **代价**：多一轮模型调用的可能。**[待实测]**：`no_action` 的转人工条数。

## V1 在哪些消息上可能比 V0 稳，在哪些上会卡住

**[待实测]**：下面全部是由代码结构推出来的**假设**，每条都写了用哪个无标签指标或 trace 来验证。真实运行之后，用数据替换或推翻它们。

| 消息类型 | 预期 | 为什么（代码依据） | 怎么验证 |
|---|---|---|---|
| 订单号写法不规范 | V1 更稳 | `fetch` 由代码清洗，V0 要先错一次 | 两者的"非法参数调用数"；V1 应为 0 |
| 单意图、给了订单号的物流查询 | 两者相当，V1 更便宜 | V1 固定 2 次模型调用；V0 约 3 次 | 成本 / 条、平均步数 |
| 多意图（问物流又要退货） | V1 可能漏数据 | classify 只能一次性报 `needs`，漏报的数据 fetch 不会补 | 读 trace：V1 草稿里"抱歉无法确认"类句子；V1 的无来源事实率 |
| 信息缺失、需要追问 | 两者都应追问；V1 更可控 | V1 的 draft 提示里明确写了"缺数据就问" | trace + 判官（越权承诺） |
| 只给邮箱、邮箱名下多个订单 | V1 稳定地不猜 | fetch 只在唯一时才继续查订单；V0 可能挑一个 | 读 trace |
| 长线程、关键信息在第 1 轮 | 两者都看完整线程；V1 classify 漏读的代价更大 | V1 的 draft 只能看到 classify 让它看到的数据 | 读 trace（迭代日志 E12） |
| 需要根据第一次查询结果再查（例：按邮箱查到订单后再查物流） | V1 只支持写死的一种连环查询 | fetch 里只写了"邮箱 → 唯一订单 → 订单 / 物流"一条链 | V1 草稿里的"抱歉无法确认"率 |
| 注入、诱导 | V1 更稳 | 模型不能决定调什么工具，最坏情况是草稿写错，路由仍由代码按标签推导 | 风险标签分布（有金标后看 INJECTION 召回） |

一句话总结（假设）：**V1 用灵活性换可预测性**。消息形态越接近 classify 设计时想到的那几种，V1 越好；越需要"查了再决定下一步查什么"，V0 越好。
