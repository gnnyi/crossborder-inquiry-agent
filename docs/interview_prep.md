> 每个答案都指向本仓库的文件、函数或数字。**标了 `【实测后填】` 的地方，现在还没有真实运行数据**（本轮开发时没有 API key）。跑完 `scripts/run_matrix.sh` 后，用 `reports/` 里的数字替换；面试前不要用估算冒充实测。
>
> 用法：先遮住答案自己讲一遍，讲不出"输入、处理、结果、我负责的部分"四件事的题，回到代码里再看一遍。

## A. Agent loop 基础

**1. 用 30 秒讲清楚你的 agent loop。**
`agents/v0.py::agent_loop`：组装上下文 → 调模型 → 模型要工具就执行、把结果放进一条 user 消息回传 → 重复，直到模型调用 `submit_response`，或撞上 `Limits` 里的某个上限转人工。146 行，不用框架。

**2. 为什么不用 LangChain / Agent SDK 写 V0？**
要能讲清每一步，并且 V0 是对照组：它是"模型掌握控制流"最朴素的形态。V1 用了 LangGraph，因为 workflow 的价值恰好是"边写死"，框架表达这个最直接。V2 也是纯 Python，因为主 / 子 Agent 之间传什么，正是要展示的内容，不能藏进框架。

**3. 模型的思考块怎么处理？**
`reply.content` 原样追加回 `messages`（`agent_loop` 第一步），思考块不剥离。Sonnet 5.5 默认开着自适应思考；只追加文字会丢状态。

**4. 一轮里模型同时调了 3 个工具怎么办？**
逐个执行，三个 `tool_result` 放进**同一条** user 消息。分成多条消息会让模型以后不再并行调用。V2 的主 Agent 提示里也鼓励一轮派多个独立任务。

**5. 你怎么让 `agent_loop` 同时服务 V0 和 V2？**
它只依赖两个注入的函数：`run_tool(name, args)` 和 `check_submit(input)`。V0 注入沙箱和契约校验；V2 的主 Agent 注入"派单给子 Agent"，子 Agent 注入"校验 findings 的来源"（`agents/v2.py`）。

## B. Tool calling

**6. 工具 schema 从哪来？**
沙箱的 4 个工具在 `sandbox/tool_schemas.json`；`submit_response` 由 `agents/common.py::submit_tool` 从输出契约自动生成，删掉代码负责填的字段，并内联 `$ref`。

**7. 客户写了 `#10231`，你的系统怎么处理？**
V0：沙箱返回 `invalid_argument: order_id must be digits only`，原样回传，模型自己改（`tests/test_v0.py::test_invalid_argument_goes_back_to_model_unrepaired`）。V1：`fetch` 节点用 `normalize_order_ref` 由代码清洗。沙箱永远不容错（ADR-2）。

**8. 为什么不干脆让沙箱容错？**
那样就测不出模型的这项能力，"非法参数调用数"指标也会失去意义。容错放在哪一层，取决于这一层的控制权在谁手里：agent 里在模型，workflow 里在代码。

**9. 模型调了一个不存在的工具呢？**
直接回错误，不发给沙箱（`test_unknown_tool_is_not_sent_to_sandbox`），否则会污染"非法参数调用"统计。

## C. 停止条件

**10. 你的 agent 什么时候停？**
五种：成功交卷；`max_steps`（10）；`max_tool_calls`（12，含重试）；两次交卷都不合契约（`contract_invalid`）；提醒一次后仍不行动（`no_action`）。每种都有测试（`tests/test_v0.py`）和单独的 `handoff_reason`。

**11. 上限的数字怎么定的？**
先验：典型物流查询 3 步，多意图 5–6 步，给一倍余量。实测平均步数和 p95 出来后再调。【实测后填：V0 平均步数 ___，撞上限 ___ 条】

**12. Sonnet 5.5 不能强制调用工具，你怎么保证它交卷？**
`tool_choice` 用 auto，加提示词；不行动时提醒一次，再不行转人工（ADR-10）。这是"模型能力变化导致控制手段要变"的例子。

## D. 失败处理

**13. 工具超时怎么办？**
由代码自动重试，最多 2 次，每次重试都是新的 `call_id`，计入调用上限（`agent_loop` 第三步）。超时是基础设施问题，不该消耗一次模型调用。

**14. 模型交的卷不合格呢？**
用和评分脚本一样的 `validate_output` 校验，错误作为 `is_error` 的 tool_result 回传，改一次；还不行就转人工（`test_bad_submission_gets_one_fix_then_handoff`）。

**15. "失败视为转人工"会不会掩盖问题？**
会，所以三个数一起报：捕获率、误拦率、失败率。"全部崩溃"也能拿到 100% 捕获率，失败率会暴露它（ADR-7）。fallback 输出带 `meta.fallback`，`label_free.py` 单独统计"agent 自己完成的比例"。

**16. runner 进程被杀了怎么办？**
`run.py` 续跑：有 output 或 error 的消息跳过；只有半截工具日志的，把日志挪到 `traces/aborted/`，不往旧日志上追加（`test_resume_skips_done_and_moves_partial_logs_aside`）。`runs/` 永不覆盖，配置不同的同名 run 会被拒绝。

## E. 上下文管理

**17. 知识库怎么给模型？为什么不用 RAG？**
全量放进 system，带缓存（ADR-5）。KB 约 2.2 万字符，约 6–7K tokens，没到需要检索的规模；RAG 会多一类"没检索到"的错误，也会让 claim 的行号依赖切块方式。

**18. 缓存省了多少？**
估算：每条消息前缀成本约 $0.038 → $0.0038，一次全量运行约省 $6（按 4 字符 ≈ 1 token、价格表未核实）。【实测后填：缓存命中率 ___，每条成本 ___】

**19. 长线程怎么处理？**
`render_message` 渲染完整线程，每一轮标明角色和时间，并提示"关键信息常在前面"。180 条里 21 条是 ≥5 轮的长线程，其中 20 条的关键信息在第 1 轮（`OVERNIGHT_REPORT.md` 1.3）。

## F. 多 Agent 取舍

**20. V2 为什么这样拆？**
按数据源拆，不按意图拆：订单、政策两个子 Agent 各自最小权限；审核不能调工具，只看代码解析出的证据（ADR-6）。

**21. 主 Agent 和子 Agent 之间传什么？**
Brief `{task, context, questions}`，Findings `{findings[{statement, source}], unresolved, notes}`，Review `{verdict, issues}`。子 Agent 看不到对话，主 Agent 漏写进 context 的信息就丢了（`agents/v2.py` 顶部）。

**22. 多 Agent 有什么代价？你量化了吗？**
成本：每条至少 4 次模型调用。割裂：`label_free.py` 的 V2 专有表——claim 来源不在任何子 Agent 返回里的比例、审核后没再审就交卷、子 Agent 无法回答的问题数。【实测后填】

**23. 那 V2 更好吗？**
【实测后填】。我的预期是不会：这个任务没有上下文压力。如果实测也是这样，结论就是"这个场景不该用多 Agent"，我会如实写进 README。

**24. 什么时候不该用 agent？**
规则确定的决策（路由）收回代码（ADR-3）；数据需求可以从分类结果确定推导的消息，用 V1 这样的 workflow 更便宜、更可预测。V0 留给"查了才知道下一步查什么"的消息。

## G. Eval 设计

**25. 没有金标时你怎么迭代？**
`scoring/label_free.py`：契约合规、幽灵引用、工具数据矛盾、无来源事实（正则抽日期 / 金额 / 订单号，看是否被 claim 覆盖）、非法参数调用、重复调用、步数、成本、延迟、缓存命中率，以及 V0-a 的"路由与自报风险标签不一致率"。全都不读金标。

**26. 幽灵引用和工具数据矛盾怎么判？**
复用 `scoring/score.py::score_message`，传一个占位标签，保证和有金标时的检查完全一致。矛盾只判日期和金额，时间戳字段允许相差一天（时区），宁可漏报不误报。

**27. 路由消融实验怎么设计的？**
V0-a 模型输出 route，V0-b 代码按 `derive_route` 推导，其他完全相同（`--variant`）。无金标时比"自相矛盾率"；有金标后比高风险捕获率和误拦率。【实测后填】

## H. 防止自己骗自己

**28. 你怎么保证迭代不是在对答案？**
四条机制：(1) 预标封在 `eval/_sealed/`，开发全程不读；(2) 报告只出汇总，逐条预测只留在 `runs/`；(3) 每次修改必须对应一类错误（`docs/iteration_log.md` 错误类别表），禁止针对单条消息打补丁；(4) `demo.py` 在盲标少于 100 条时拒绝展示真实模型的判断，防止锚定。

## J. 上线边界

**30. 这个东西能上线吗？上线的话边界在哪？**
按策略表分三档：无风险标签 → AUTO_REPLY；退款、赔偿、价格承诺、送达承诺、差评威胁 → 草稿给人审；拒付 / 法律、身份不符、注入 → 直接转人工。路由由代码按策略表决定，模型只负责识别风险。上线前必须满足：有金标后高风险捕获率 ≥ 90%、误拦率 ≤ 10%（`score.py` 的目标值）；判官校准一致率 ≥ 90%。现在一条都还没验证，所以**现在不能上线**。

## 最难的 5 道追问（诚实版）

**H1. 你的 eval 集是 AI 生成的，凭什么可信？**
不完全可信，我也没这么说。能说的是：(1) 消息的生成意图和预标封存，我自己盲标，用 `tools/agreement.py` 算我和预标的一致率，一致率低的类别说明要么题目有歧义，要么预标错了；(2) 我列出了 20 条最不像真人的消息（`OVERNIGHT_REPORT.md` 3.3），计划删到 150 条左右；(3) 这套 eval 测的是**架构之间的相对差异**，不是"在真实客户上的绝对准确率"，相对差异对数据分布的敏感度低一些，但不是零。真正的校准办法是拿 5–10 条真实询盘的类型做对照，这一步还没做。

**H2. 金标只有你一个人标，怎么知道标得对？**
不知道，这是最大的局限。缓解办法：标注规范 `eval/guideline.md` 里写判例，同类情况按判例标；隔一段时间重标一个子集，测自己的前后一致率；和 AI 预标的分歧逐条复核。单人金标适合比较架构，不适合宣称"准确率 95%"。

**H3. 你迭代了几轮，具体改了什么？**
【实测后填】。如果还没跑，就实话实说：基础设施和三种架构都写完、测完了，真实迭代还没开始，然后讲清楚迭代流程和错误类别表（`docs/iteration_log.md`）。编造一个迭代故事，会在第二个追问时露馅。

**H4. 你的"无来源事实"检测只看日期、金额、订单号，"您的订单已发货"这种话呢？**
抓不到。这类要靠 LLM 判官（接口 `scoring/score.py::LLMJudge`，还没实现）。判官本身也要先和人工标注校准，一致率 ≥ 90% 才能用；校准之前，判官结果不进 README 的结果表。确定性检查的价值是"零误报、零成本"，它是底线，不是全部。

**H5. 这个项目和真实工作有什么关系？你在真实工作里会这么做吗？**
会，但顺序相反。真实工作里应该先拿真实工单（哪怕 50 条）做人工分析，再决定要不要 agent。这个项目用虚构品牌是因为拿不到真实数据，所以把力气花在了"能迁移的部分"：输出契约、风险路由、无标签指标、预算熔断、失败转人工。这些在真实场景里可以直接复用。它延续自 `order-incident-agent`，新增了评测体系、风险路由和架构对比。
