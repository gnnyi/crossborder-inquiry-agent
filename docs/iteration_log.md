## 迭代规则（任务书阶段 2，原样执行）

1. 全量跑 180 条：`python run.py --arch V0 --variant b --run-id v0b-r1`
2. 出无标签报告和失败清单：`python scoring/label_free.py runs/V0-b/v0b-r1 --failures --out reports/v0b-r1.md`
3. 打开 `runs/V0-b/v0b-r1/label_free_failures.json`，**逐条读 trace**（`runs/V0-b/v0b-r1/traces/<msg_id>.json`，或者 `python demo.py <msg_id> --arch V0 --replay runs/V0-b/v0b-r1`），每条给一个下表里的类别。
4. 选占比最大的一类，按成本从低到高修：**工具描述 / 错误信息 → prompt → 代码约束 → 架构**。
5. 换一个 run_id 全量重跑，确认目标类别下降、其他指标没变差。
6. 修复只对少数几条有效时，写明"可能过拟合"。

两条红线：不在 prompt 或代码里写只为某一条消息存在的规则；修复前后都**不打开** `runs/*/outputs/` 去看具体判了什么意图、风险、路由（盲标完成之前）。读 trace 只为了归类失败机制。

> 第 2 条红线和"逐条读 trace"有张力：trace 里有模型交的卷。我的做法是读 trace 时只看工具调用、错误信息、claims 和停止原因，跳过 `intents` / `risk_flags` / `route`。如果你觉得这仍然有锚定风险，就先盲标、再迭代——见 `ITERATION_REPORT.md` 第 4 节的顺序建议。

读法：

- **重跑波动很大**：同一配置，幽灵引用 4 条 vs 0 条，转人工 0 vs 2，AUTO_REPLY 占比差 5 个百分点。所以任何"1–2 条"的变化都不能当成改进；路由占比在有金标之后也要按这个波动看。
- **第 1 轮（E4-B）**：目标类别 3 → 0、0（两次运行都是 0）。方向一致，但基数只有 3 条，**可能过拟合，只能算"没有反例"**。
- **第 2 轮 · E4-C 举例订单号**：
  - **读 trace 后找到根因**：示例订单号 "10231" 来自**我们自己的 prompt 和工具描述**（`get_order` / `get_tracking` 的参数说明写着 e.g. "10231"），而它恰好是沙箱里一位真实客户的订单号。模型向客户索要订单号时照抄了这个例子。
  - 修复：工具描述层，示例号改成格式说明（去掉 `#`、字母前缀和空格）；prompt 层，在 `CLAIMS` 里加一句"向客户索要订单号时不要举例号，回复里的任何订单号都会被当成真实订单"。
  - 结果：2、2 → 0。
- 剩下的"无来源事实"都是解析器误报（"25th"、"$12.95." 这类写法），不是模型的问题。
- **新出现 1 条工具数据矛盾**：claim 把两件商品的单价引用反了（`items[0]` 和 `items[1]` 对调）。只出现 1 次，暂不处理，记为 E5 观察项。
- 副作用：成本、步数、延迟都在波动范围内，没有变化。

## 第 4 轮（已写好，未运行）

- 针对的类别：E7 被迫转人工 `contract_invalid`（4 次运行共 4 条）。读 trace 后发现两种机制：
  1. 模型调用 `submit_response` 时参数是**空对象** `{}`（stop_reason 是 tool_use，不是被截断），收到"intents: None is not of type 'array'"之类的错误后又交了一次空的；
  2. KB 来源的 `lines` 只写了一个数（`[16]`），jsonschema 只报"not valid under any of the given schemas"，并把整个 reply 原样贴回去，模型看不出错在哪，第二次交了同样的错误。
- 改法：属于**工具错误信息层**。`agents/common.py::explain_submit_errors` 把这两种看不懂的错误改写成能照着改的说明：
  - 空提交：给一句"参数是空的，请把每个字段都填上重交"；
  - oneOf 错误：逐条指出哪条 claim 的哪个字段不对，并附上两种来源的格式。
  校验规则本身不变。
